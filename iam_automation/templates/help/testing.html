Operating model

How the workspace works

  1. Preflight: the desktop launcher discovers the local SharePoint or OneDrive folder, validates Access, runtime SQLite, folders and local workspace, then synchronizes a local SQLite copy.
  2. Identity gate: the current Windows or workstation identity is recorded for traceability. The application login is a separate account and does not use the workstation password.
  3. JSON-first workflow: requests and bug reports are shared as JSON files in the synchronized workspace so other workstations can see them without waiting for a database publication.
  4. Application workflow: users create requests, reviewers assign and decide them, and approved requests enter the controlled publication queue.
  5. Runtime publication: user, role and password changes are local until an Application Admin or Master Admin publishes the runtime SQLite snapshot. Access publication remains a protected administrative operation.

Before testing

Preconditions

  • Start the app through the platform launcher.
  • Confirm the preflight status is READY.
  • Confirm the SharePoint path is the intended synchronized workspace.
  • Use a test account assigned to the scenario.
  • Do not use production data or real passwords.
  • Refresh the workspace before testing a change from another computer.

Report quality

When a test fails

  1. Keep the failing state open long enough to capture the exact message.
  2. Record the test case ID, user, role, computer or VDI and page.
  3. Write the numbered steps that reproduce the problem.
  4. State what was expected and what actually happened.
  5. Attach a screenshot only after removing passwords, tokens and sensitive employee data.
  6. Submit it from Report a bug; do not edit the JSON manually.
