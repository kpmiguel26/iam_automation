The operating rule

Evidence first. Decision second.

A profile brings together evidence from several systems. It does not mean that one source automatically wins. Compare the source, file, timestamp and match explanation before applying or submitting a change.

1

Find

Search by name, email, identifier, vendor or engagement and narrow the result with filters.

2

Compare

Open the profile tree or Updates and compare each source value with its timestamp.

3

Act

Review, apply locally, submit for approval or publish according to your authorization.

Quick start

Five-minute review

Use this sequence during UAT and daily operations.

Review workflow
  1. Open Employees and search. The directory waits for a search or filter before loading a large result set.
  2. Open the employee name. Start with the canonical identity, then expand each source platform.
  3. Check identifiers, source file, observed time, status and engagement values. Keep conflicting evidence visible.
  4. For an incoming file, open Updates and review the match result, reason and field-level differences.
  5. Choose the action that matches your authority. Confirm the result in history and, if needed, publish the runtime snapshot.

Action guide

Available actions depend on your role and the current workspace policy.

Shares the runtime SQLite snapshot with other workstations after local work.

Expand a platform to see its identifiers, mapped engagement snapshot and complete source fields. Lineage tells you which file and observation produced a value.

New files are staged before any action. Review the match status and match reason, then compare current and incoming values field by field. An unmatched candidate is evidence to review, not permission to guess.

  1. Open the employee or candidate.
  2. Check source ID, file, row and observed time.
  3. Select only the fields that should be changed.
  4. Apply locally if authorized, or submit for approval.
  5. Confirm the new version and actor in history.

History records version, actor, source, file, changed fields and previous/current values.

  • Apply locally: writes the approved result to this workstation and creates history.
  • Publish: distributes the runtime SQLite snapshot; it does not write AccessNow, Fieldglass or another authoritative source.
  • Refresh: another workstation must refresh to receive a published snapshot.

For each scenario, retain the source file/hash, batch and row counts, match explanation, timestamps, finding classification, review note, audit event and export checksum.

□ Input row is accepted, quarantined or rejected with evidence.
□ Match is repeatable and ambiguity is visible.
□ Conflicts retain source and temporal context.
□ Local apply/publish result is attributable.

Troubleshooting

When something looks wrong

Employee not foundSearch by identifier or email, remove restrictive filters and confirm the workspace is refreshed.
Values disagreeKeep both values visible. Compare source, file, row and timestamp; do not silently overwrite another source.
History is missingCheck whether the action was only submitted, applied locally or published. These are separate steps.
