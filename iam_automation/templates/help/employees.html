Operations guide

Employees

How to find an employee, understand source-owned data and submit a controlled change.

Open Employees
Important: Employee profiles are primarily read-only. SRS, AccessNow and Master Roster Lock keep separate values; the employee profile shows them together without allowing one platform to overwrite another.

Quick start

Find and understand an employee

  1. Open Employees from Operations.
  2. Search by name, email, vendor identifier or vendor. You can also filter by status, source and engagement.
  3. Select the employee name to open the read-only profile tree.
  4. Expand a source platform to inspect its identifiers, snapshots and all captured fields.
  5. Use Review source updates when a new file has pending changes that require field-level review.

Source ownership

Who owns what?

  • SRS: supplier and Fieldglass worker details.
  • AccessNow: active/termination status and AccessNow identifiers.
  • Master Roster Lock: roster and vendor engagement values.
  • Administrative change: canonical profile fields after approval.

Step-by-step

Using the employee area

Open each topic for the action and the expected result.

Use the search field for a broad lookup. Status, vendor and source filters can be combined. The directory loads results only after a search or filter is submitted.

  • Source: filters by the platform that supplied an identifier.
  • Engagement: searches vendor, program, project, role, location and statement of work.
  • Review: indicates open discrepancies that deserve attention.

The first page is a read-only overview. The tree is organized as:

Employee
└─ Canonical identity
└─ Source platforms
├─ SRS
├─ AccessNow
└─ Master Roster Lock
└─ Immutable history

Expand a platform to see its identifiers, mapped engagement snapshot and all source fields. Values from different platforms are intentionally shown side by side.

Each source accordion is evidence from that platform. If values disagree, compare the source file and observed timestamp before deciding which business process should correct it.

  • Identifiers are source-owned and should not be manually changed casually.
  • Mapped fields provide a convenient summary; “All fields” shows the complete source lineage.
  • A source update should change only that source’s snapshot, never another source’s snapshot.

When a source file is ingested, it is staged first. Open Updates to review matched employees, new candidates and possible duplicates.

  1. Open the employee or candidate.
  2. Compare current value and incoming value field by field.
  3. Select only the fields that should be applied.
  4. Apply locally only when authorized, or submit for approval.
  5. Confirm the new version in the employee history.

Click Edit profile on the employee overview. The edit page contains the full form and the required Business reason.

Editing does not save directly. Submitting creates a request. A reviewer must approve it before the canonical profile changes, and the change is then recorded in immutable history.

History records the version, actor, source, file, changed fields and previous/current values. Local application and SQLite publication are separate steps.

  • Applied locally: the change exists on this workstation and history is available immediately.
  • Published: an administrator shares the SQLite snapshot with other workstations.
  • Refresh: another workstation must refresh its workspace to receive the published snapshot.

Troubleshooting

If something looks wrong

Employee not foundCheck the directory search and confirm the local workspace has refreshed.
Values disagreeOpen each source accordion and compare source, file and timestamp. Do not overwrite another source to “fix” it.
History is missingConfirm the change was applied locally. Publishing only shares the local history; it does not create it.
