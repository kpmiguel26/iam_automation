Phase 1 boundary

Review evidence. Keep decisions with people.

The Business Rules Engine checks imported evidence and creates review findings. It is advisory-only: a rule can highlight something that needs attention, but it never makes the business decision for you.

Important: Rules do not block imports, reject or approve hires, modify canonical employees, change permissions, write back to source systems or make provisioning decisions.

How rules run

BEFORE and AFTER

Both phases create advisory findings only.

No import blocking
B

BEFORE

Checks normalized rows while the incoming report is being prepared, before the source adapter saves the data. The match is attached to the imported record after the batch is created.

A

AFTER

Checks records after the import has committed its evidence to SQLite. This is the phase used when a rule needs persisted or cross-source evidence.

Source→Import→Persist→Rule evaluation→Finding→Human review

Historical data: activating a rule checks historical imports for AFTER rules. BEFORE rules start applying on the next import and do not retroprocess older files.

Creating a rule

The wizard asks for the business meaning of the check and creates the rule as DRAFT.

Building a condition

Operand types

An operand is the information on one side of a comparison.

Field

A report field

Reads a value such as assignment_status, email or termination_date. A field can be selected from a specific source.

Literal

A fixed value

A value you type into the rule, such as TERMINATED, 0, 30 or a date.

Derived

A calculated value

A value calculated from other operands. The current derived function is business_days_between.

Date format: dates can use ISO format such as 2026-09-14 or US format such as 09/14/2026. A date that cannot be read will not match a date comparison.

More than one check

Composite conditions

Combine simple checks when one field is not enough.

Use ALL when the finding should appear only when all parts of the situation are present. Example: the status is terminated AND the rehire window is within 30 business days.

Use ANY when different conditions should lead to the same review. Example: an email is missing OR a required identifier is missing.

Use NOT carefully to describe an exception. Explain the exception in the rule description so reviewers understand why the finding appears.

Practical example

30-business-day rehire review

This rule identifies a situation for human review; it does not approve or reject the rehire.

Advisory finding
Access status IN [TERMINATED, DEACTIVATED]
AND
Date window business_days_between(termination_date, onboarding_date) BETWEEN 0 AND 30
1. Status

The AccessNow observation must be TERMINATED or DEACTIVATED.

2. Dates

The engine counts configured business days from termination to onboarding.

3. Review

A match is shown in Quarantine for a person to investigate and disposition.

Calendar matters: weekends, operating days and enabled holidays affect the count. Confirm the configured calendar before interpreting a boundary result.

Rule status

Rule lifecycle

DRAFT→Test→ACTIVE→DISABLED
  • DRAFT: created but not running.
  • Test: previews matches without creating findings or changing status.
  • ACTIVE: runs during the selected phase.
  • DISABLED: no new findings; existing findings remain for review.

Troubleshooting

Check these items before changing the rule.

No matchesConfirm the source scope, normalized value and operator. Use Test on a specific batch when narrowing the issue.
Field is not in the selectorChoose the correct report first. The field must be active and enabled for rules, or it may not have been observed yet.
Date cannot be evaluatedUse ISO or MM/DD/YYYY. Check that both dates are present and valid; an unreadable date does not match.
Cross-source field is unavailableCross-source checks need linked evidence for the same matched worker. Without that relationship, only the current source record is available.
Test works but older data does notHistorical evaluation is available for AFTER rules. A BEFORE rule does not retroprocess older imports.
BEFORE rule did not run on old filesThat is expected. Import the source again, or use an AFTER rule when the check needs historical evidence.
Finding appears duplicatedThe same rule version and record are deduplicated. Check whether a new rule/version or a separate source record produced the second finding.
Calendar changed the resultReview operating days, enabled holidays and the configured date boundary. Business-day results depend on that calendar.
